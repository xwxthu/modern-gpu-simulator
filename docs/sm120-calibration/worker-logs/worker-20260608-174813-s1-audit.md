## 1. SM120 Parameter Taxonomy

The two SM120 configs are not currently separated into architecture base, SKU overlay, and calibration results. They are complete flat configs. The only active deltas between `SM120_RTX5070_TI` and `SM120_RTX5060` are:

- `-gpgpu_n_clusters`: 70 for 5070 Ti, 30 for 5060.
- `-gpgpu_n_mem`: 16 for 5070 Ti, 8 for 5060.
- `-gpgpu_clock_domains`: `2580:2580:2580:14000` for 5070 Ti, `2640:2640:2640:14000` for 5060.

### SKU Specification Parameters

These should live in per-GPU overlay first, with source/provenance fields:

- SM count / cluster topology: `-gpgpu_n_clusters`, `-gpgpu_n_cores_per_cluster`.
- Memory partition/channel topology: `-gpgpu_n_mem`, `-gpgpu_n_sub_partition_per_mchannel`, `-gpgpu_n_mem_per_ctrlr`.
- Public or device-query resource limits: `-gpgpu_shader_registers`, `-gpgpu_registers_per_block`, `-gpgpu_shader_core_pipeline`, `-gpgpu_shader_cta`, `-gpgpu_shmem_size`, `-gpgpu_shmem_sizeDefault`, `-gpgpu_shmem_per_block`.
- Compute capability is not a per-GPU SKU overlay parameter for S2; `-gpgpu_compute_capability_major` and `-gpgpu_compute_capability_minor` have single ownership in `SM120_BASE` as architecture parameters, with device query used only to verify the expected CC 12.0 value.
- Device/runtime limits if confirmed per device: stack/heap/sync/pending launch/max concurrent kernel.
- Clock domains: `-gpgpu_clock_domains`, but this needs locked-clock or recorded-clock methodology. Current 5060 comments explicitly call it smoke-ready, not controlled-clock calibration.
- Board/memory-facing values when confirmed by official tools or device query: `-gpgpu_dram_buswidth`, memory clock, memory partition count, modeled L2 size mapping.
- AccelWattch/power XML values should be per-GPU if used. 5060 XML is currently copied and explicitly uncalibrated.

### SM120 Architecture Parameters

These should be common `SM120_BASE` unless later evidence proves SKU variation:

- Compute capability and trace mode defaults, with single ownership in `SM120_BASE`: `-gpgpu_ptx_force_max_capability 120`, `-gpgpu_compute_capability_major 12`, `-gpgpu_compute_capability_minor 0`, `-gpgpu_coalesce_arch 120`.
- Subcore structure: `-gpgpu_sub_core_model 1`, `-gpgpu_num_sched_per_core 4`, `-num_subcores_in_SM 4`, `-gpgpu_num_sp_units 4`, `-gpgpu_num_sfu_units 4`, `-gpgpu_num_int_units 4`, `-gpgpu_num_tensor_core_units 4`, `-gpgpu_pipeline_widths`.
- Basic SM common resources: warp size derived by `-gpgpu_shader_core_pipeline 1536:32`, register-bank count `-gpgpu_num_reg_banks 8`, shared-memory bank count `-gpgpu_shmem_num_banks 32`.
- Blackwell/SM120 cache hierarchy shape if validated as architectural: adaptive L1/shared mode, `-gpgpu_unified_l1d_size 128`, L1/IL1/TEX/CONST/L0 cache format, L0I enablement, per-subcore L0 constant cache.
- Remodeled model switches: `-is_fetch_and_decode_improved`, `-is_extra_traces_enabled`, `-is_SM_remodeling_enabled`, `-is_ibuffer_remodeled_enabled`, `-fetch_decode_width`.
- Trace-enhanced categories: branch/half/uniform/predicate/misc categories and specialized TEX unit in `trace.config`.
- Shared DP-pipeline and FP32/INT pipeline policy if SM120-common: `-is_dp_pipeline_shared_for_subcores`, `-is_fp32ops_allowed_in_int_pipeline`, `-is_fp32_and_int_unified_pipeline`.
- Tracer requirement: enhanced operands/control bits and Blackwell opcode map are architecture requirements for the remodeled path, not per-GPU calibration knobs.

### Calibration Parameters

These should be generated or at least tagged by measurement source:

- Instruction latency/initiation in both `gpgpusim.config` and `trace.config`: PTX latencies, trace latencies, tensor latency/rate/extra latency, branch/half/uniform/predicate/misc latency and initiation.
- Memory/cache geometry and latency: `-gpgpu_cache:dl1`, `-gpgpu_l1_banks`, `-gpgpu_l1_banks_hashing_function`, `-gpgpu_cache:dl2`, L2 associativity/sets/MSHR shape, `-gpgpu_l2_rop_latency`, `-dram_latency`, `-memory_l1d_minimum_latency`, `-constant_cache_latency_at_sm_structure`, shared-memory minimum/extra latencies.
- DRAM timing and scheduling: `-gpgpu_dram_timing_opt`, `-gpgpu_dram_scheduler`, FR-FCFS queue sizes, return queue sizes, bus width/burst/frequency ratio if not directly sourced.
- Address mapping/hash/indexing: `-gpgpu_memory_partition_indexing`, `-gpgpu_mem_addr_mapping`, `-dram_bnk_indexing_policy`, `-dram_bnkgrp_indexing_policy`.
- Pipeline queue and bandwidth knobs: operand collector counts, `-gpgpu_reg_file_port_throughput`, `-memory_subcore_queue_size`, `-memory_intermidiate_stages_subcore_unit`, `-memory_sm_prt_size`, per-access queue sizes, `-memory_num_scalar_units_per_subcore`, `-memory_subcore_link_to_sm_byte_size`, load/store half-bandwidth toggles.
- RF/cache and dependency timing: `-is_rf_cache_enabled`, RF port counts, max RF latency, RF write-queue size/pops, read granularity by op class, `-scoreboard_war_*`, barrier stall cycles, IMAD.WIDE issue-port busy cycles, stall/yield behavior.
- PRT/interwarp coalescing: number of coalescers, PRT policy, interwarp tables/quanta/threshold, cluster count for PRT policy.
- Kernel launch/TB launch latency if used for end-to-end cycle correlation.
- Power: all AccelWattch XML activity/static parameters and power validation inputs.

### Temporary / Uncalibrated Assumptions

High-risk assumptions visible today:

- RTX5060 is derived from RTX5070 Ti and only edits SM count, memory partition count, and clocks. The comment says "draft derived" and "smoke-ready draft, not a controlled-clock calibration" in `SM120_RTX5060/gpgpusim.config` lines 52-64.
- RTX5060 retains 5070 Ti L1/L2/DRAM timing, cache shapes, queue sizes, remodeled latencies, interconnect, address mapping, and all microarchitecture knobs.
- RTX5060 power XML is copied from 5070 Ti and not calibrated, per `SM120_RTX5060/accelwattch_sass_sim.xml` line 2.
- `-gpgpu_occupancy_sm_number 120` is identical across both configs. It appears to encode architecture/compute capability rather than actual SM count, but it needs provenance because the name reads like an SM count.
- Both SM120 trace configs are identical, so any SKU-specific trace latency/throughput differences are not represented.
- `-gpgpu_cache:dl2 S:128:128:24,...` is identical for 5070 Ti and 5060 while the 5060 comment says 24 MiB L2 is modeled via 8 memory partitions. This mapping needs an explicit formula or generator check in S2/S4.
- `-gpgpu_mem_addr_mapping` and `-gpgpu_memory_partition_indexing 2` are inherited. No evidence yet that 5060 and 5070 Ti share the same Blackwell partition/hash behavior.
- `-gpgpu_dram_timing_opt`, `-dram_latency`, `-gpgpu_l2_rop_latency`, and queue sizes are copied; no locked-clock measurement evidence is attached.

## 2. Tooling Coverage And Gaps

### `util/tuner`

Coverage:

- Has the Accel-Sim-style microbenchmark suite tree under `simulator-remodeled/util/tuner/GPU_Microbenchmark/ubench`.
- Covers many legacy calibration categories: system/core config, execution units, RF bandwidth, L1/L2/shared/memory latency and bandwidth, cache write policy, MSHR, line/sector/access grain, atomics, tensor half tests.
- `tuner.py` can parse lines beginning with `-` from ubench output and replace matching keys in a template.

Gaps:

- No SM120 hw_def. `hw_def.h` selects `volta_TITANV_hw_def.h`, so an SM120 run would be configured with the wrong public hardware assumptions.
- The tuner microbenchmark `common.mk` lacks `sm_120` and still assumes `CUDA_PATH ?= /use/local/cuda-10.1/`; this conflicts with the project target of CUDA 13.2.
- The embedded tuner template has no L0I/remodeled SM/RF/PRT/interwarp options, so even successful microbenchmark output cannot generate a complete modern SM120 config.
- The template still includes legacy `-gpgpu_l1_latency` / `-gpgpu_smem_latency` keys, while current SM120 configs use remodeled memory latency knobs instead.
- `tuner.py` has no schema, provenance, layering, units, or validation. Missing keys silently remain as template placeholders or legacy defaults.
- The documented 16-point search only covers warp scheduling, L2 interleaving granularity, L2 hash, and memory scheduler. Modern remodeled parameters add many more non-direct knobs, so the search design is incomplete for SM120.
- The tuner is not integrated with `dsp5060` collection constraints or a local simulation workflow.

### `util/hw_stats`

Coverage:

- Can create hardware profiling run directories.
- Supports `--nsight_profiler`, `--disable_nvprof`, and `--nsys_profiler`.
- Can collect GPC cycles and a large fixed list of Nsight Compute counters.

Gaps:

- Default path still tries nvprof unless disabled, and error text is inconsistent.
- Metric lists are hardcoded and not checked against current Nsight Compute metric availability for SM120/CUDA 13.2.
- No official-tool hardware spec collector for SM count, clocks, memory bus, L2, partitions, supported shared memory modes, etc.
- No controlled-clock protocol, no clock capture per run, and no normalized metadata format.
- No staged "read direct first, microbenchmark second, targeted correlation last" flow.
- Hardware data layout is still Accel-Sim-era `hw_run/device-*/cuda_version/...`; no S1 evidence of an SM120 calibration-result schema.

### `util/tracer_nvbit`

Coverage:

- Has a dedicated SM120 smoke script. It defaults to `ARCH=sm_120`, validates `Binary Version 120`, requires NVBit 1.7.5, checks enhanced execution metadata, and runs the simulator with `SM120_RTX5060`.
- `run_hw_trace.py` supports trace generation for benchmark suites and per-benchmark argument overrides.
- Enhanced trace tooling captures operands/control bits needed by the remodeled model. `traced_instruction.cc` selects the Blackwell opcode map for binary version 120; `control_bits.cc` decodes stall/yield/barrier fields.

Gaps:

- Smoke script defaults to CUDA 12.8, not CUDA 13.2.
- Smoke validates functional closure only. It explicitly does not measure performance accuracy, cache/memory stats alignment, or calibrated timing.
- No calibration harness ties trace generation, hardware counter collection, simulator run, and plot/correlation into one reproducible staged flow.
- Enhanced trace dependency means benchmark binaries must expose SASS/control bits; missing-control-bit hybrid behavior must be tracked in calibration metadata.

### `util/job_launching`

Coverage:

- `define-standard-cfgs.yml` includes `RTX5060` and `RTX5070_TI` aliases.
- Launching and `get_stats.py` can run trace simulations and collect simulator statistics from logs.
- Existing README shows `run_simulations.py` and `get_stats.py` use with `SM120_RTX5060`.

Gaps:

- Config aliases point to flat configs, not layered/generated config outputs.
- No generated sweep configs for SM120 calibration stages.
- No remote collection orchestration for `dsp5060`.
- No first-class mapping from calibration result files to runnable configs.
- `get_stats.py` parses simulator logs but does not know about remodeled stats provenance or hardware-unit bridges.

### `util/plotting`

Coverage:

- `plot-correlation.py` can merge simulator CSVs with hardware data and compute correlations.
- Has generic GPC cycles mapping with `hw_name="all"`.

Gaps:

- `correl_mappings.py` has no RTX5060 / RTX5070 Ti / SM120 config-to-hardware-name map.
- Many mappings use nvprof-era metric names. Nsight Compute SM120 names and units need review.
- Cycle conversions mix fixed MHz assumptions for older cards with generic GPC cycles. SM120 needs locked or recorded clocks and explicit cycle source selection.
- No mapping for remodeled stats such as L0I, RF cache behavior, control-bit dependency stalls, PRT/interwarp coalescing, subcore memory queues, or barrier stalls.
- No outlier policy or benchmark subset specific to SM120 calibration stages.

## 4. Comparison With Reference Accel-Sim

Reference `accel-sim-framework` at `3016c658...` differs from modern in several important ways:

- Reference tuner does not vendor `GPU_Microbenchmark` directly under `util/tuner`; `get_ubench.sh` sparsely clones `gpu-app-collection-partial/src/cuda/GPU_Microbenchmark` from `accel-sim/gpu-app-collection` lines 1-22.
- Modern vendors `simulator-remodeled/util/tuner/GPU_Microbenchmark`, but that vendored copy is stale for SM120: no SM120 hw_def and no `sm_120` in common make flags.
- `tuner.py` is effectively the same simple key-replacement script in both repos. It has not been extended for modern/remodeled parameters.
- `config_template/gpgpusim.config` is effectively legacy in both repos. It does not include modern remodeled blocks (`-is_L0I_enabled`, `-is_SM_remodeling_enabled`, RF cache, PRT/interwarp, barrier stall, etc.).
- Reference README/tuner flow expects: get ubench, provide hw_def, compile/run microbenchmarks, run tuner, copy generated config, then run targeted search and correlator. Modern has the docs and some SM120 config aliases, but not a complete SM120-compatible tuner pipeline.
- Modern adds SM120 flat configs and job-launch aliases, plus an SM120 smoke tracer script. These are functional/stability additions, not Accel-Sim-style calibration infrastructure.
- Plotting/correlation still mostly reflects original Accel-Sim mappings and lacks SM120 devices, metric names, and modeled-stat bridges.

Breakpoints that must be addressed before S4 can generate complete SM120 configs:

- A generated config from current tuner would omit every remodeled option and could silently run the wrong model defaults.
- A current tuner microbenchmark build would not target `sm_120`.
- A current tuner run would use Volta hw_def unless manually edited.
- Current correlation mapping cannot robustly pair `RTX5060`/`RTX5070_TI` configs with hardware data names or SM120 metric units.
- Current `hw_stats` cannot serve as authoritative hardware-spec collection and is not CUDA 13.2/SM120 metric-validated.

## 5. S2 Configuration Layering Input

Recommended layout concept:

- `SM120_BASE`: architecture model and validated SM120-common defaults.
- Per-GPU overlay: physical SKU facts and board/device limits.
- Calibration results: measured/tuned values with provenance, tool versions, clock state, workload/microbenchmark, and confidence.

### Put First In `SM120_BASE`

- Compute capability and arch flags: PTX force max 120, CC 12.0, coalesce arch 120, trace/SASS mode expectations.
- Remodeled model enablement: L0I enabled, extra traces enabled, SM remodeling enabled, improved fetch/decode, remodeled ibuffer, subcore count.
- Common subcore/EU topology: 4 schedulers/subcores, SP/SFU/INT/Tensor unit counts, pipeline widths, subcore model, warp size/pipeline shape if verified as SM120-common.
