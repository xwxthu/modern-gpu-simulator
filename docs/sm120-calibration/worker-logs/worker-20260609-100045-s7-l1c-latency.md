# S7 L1C Latency Worker Log

## Purpose

Fix or precisely bound the PTX-mode L1C dispatch latency underflow for
parameter constant accesses. The assigned blocker was a routed
`param_space_kernel` / `CONST_ACC_R` access reaching
`ldst_unit_sm::dispatch_to_memory_access_queue_l1Ccache()` with
`m_latency_of_mem_operation_at_sm_structure == 0`, causing
`constant_cache_l1_latency_queue[inst_latency - 1]` to underflow to
`4294967295`.

The fix must be root-cause oriented, preserve trace-mode MICRO25/remodeled
latency behavior and existing PTX shared/global/local/constant semantics,
avoid magic dispatch fallbacks or calibrated-config changes, and avoid
SM120/RTX5060 hard-coded values.

## Actions

- Read the supervisor log, overall plan, immediate parameter-constant routing
  worker log, and prior LD/ST trace-metadata worker log.
- Inspected PTX memory-space resolution:
  - `core_t::execute_warp_inst_t()` calls
    `ptx_thread_info::ptx_exec_inst()` for active lanes.
  - PTX `ld_exec()` calls `decode_space()`, which resolves
    `param_space_unclassified` to `param_space_kernel` for kernel parameters.
  - `ptx_exec_inst()` records the resolved `last_space()` and address on the
    dynamic `warp_inst_t`.
- Inspected memory latency generation:
  - PTX/non-trace `warp_inst_t::generate_mem_latencies()` assigns
    `constant_cache_latency_at_sm_structure` when `space.is_const()`.
  - `memory_space_t::is_const()` covers both `const_space` and
    `param_space_kernel`.
  - `generate_mem_accesses()` classifies `const_space` and
    `param_space_kernel` as constant-cache accesses.
- Identified the root cause: remodeled PTX decode generated load/store latency
  metadata before functional PTX execution resolved the instruction's final
  memory space. The later functional execution and access generation correctly
  produced `param_space_kernel` / `CONST_ACC_R`, but the SM-structure latency
  field remained at its decode-time zero.
- Changed the PTX/non-trace branch of `SM::func_exec_inst()` to regenerate
  memory latencies after `execute_warp_inst_t(inst)` and before
  `inst.generate_mem_accesses()` for loads/stores.
- Left the trace-mode branch unchanged.
- Did not add a fallback/clamp in L1C dispatch, change calibrated config
  values, edit accepted configs, edit generated bulk outputs, edit calibration
  `latest`, create fake metrics, or run simulator workloads on `dsp5060`.
